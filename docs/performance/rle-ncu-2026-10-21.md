## Hardware-counter evidence

Six baseline and six after Nsight Compute 2025.1.1 reports cover 1,048,576
and 4,194,304 items, with run lengths 1, 16 and 4096. Each report contains five
launches: LCPP init/compaction/lengths, then CUB init/main. All launches complete
19 replay passes. All profiled operations pass CPU/LCPP/CUB output validation.

Collection uses kernel replay, `--cache-control all`, `--clock-control none`
and eight sections: SpeedOfLight, LaunchStats, Occupancy, SchedulerStats,
WarpStateStats, MemoryWorkloadAnalysis, SourceCounters and InstructionStats.
These are cold-cache counter measurements with unlocked clocks, not the
warm-cache CUDA-event benchmark. Do not sum their kernel durations or use
instrumented application event timings as performance results.

For run16/run4096 at 4M, LCPP/CUB main achieved occupancy is approximately
47% on both sides. Main-kernel occupancy alone therefore does not explain the
gap. LCPP has an extra bandwidth-heavy offset-to-length pass for dense output.
Its main kernel also reports 264308 excessive theoretical global sectors for
all-unique input. The existing per-thread predecessor reads are strided by 15
input elements. The source-level optimization targets these redundant loads.

Stall values above are average cycles per issued instruction, not percentages
of application time. Excessive theoretical sectors are source-counter
diagnostics, not DRAM-byte measurements. The CUB main kernel has its own
uncoalesced accesses and barrier stalls; no individual counter establishes
the complete end-to-end performance difference.

Metric interpretation follows the NVIDIA
[Nsight Compute profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/).

finished. It uses the same recipe and the frozen retained executable. All six

export, with no profiler errors. Counter durations remain separate from the

Across all six cases, excessive theoretical global sectors fall by 91.37% to
93.53%. This supports the intended reduction in strided predecessor accesses;
it does not imply a 91-94% reduction in total DRAM traffic. Registers decrease
from 73 to 72, while achieved occupancy remains close to the baseline and CUB.
The change does not remove block barriers or reduce the three-kernel pipeline.

For all-unique 4M input, the unchanged lengths kernel still reaches 85.53% of
peak DRAM throughput and reports 230.60 long-scoreboard cycles per issue.
Its excessive theoretical global-sector count is unchanged at 425983. The
additional offset read and lengths write therefore remain an important dense
output cost, even after the predecessor-load improvement. Removing that pass
without increasing main-kernel work requires a separate validated design.

## Retained implementation

Only the CUDA adjacent-compaction path that stores run offsets changes.
Each lane obtains the previous lane's final input item with `warp_read_lane`.
The first lane of each warp reads the predecessor from global memory, with
guards for the first input and partial tiles. This reduces predecessor global
loads from one per active thread to one per active warp.

Selection/Partition and Unique without run offsets retain their existing
selection logic. Tile policy, look-back state, temporary-storage queries,
three-kernel RLE pipeline and the offset-to-length kernel are unchanged.

Two length-kernel experiments were discarded: warp forwarding of the next
packet's first offset, and issuing two packet loads before their stores.
They passed output checks but did not show a stable improvement sufficient
to retain the added instructions. Some exploratory processes overlapped an
unrelated libuipc GPU benchmark; these are not formal performance evidence.
